# 計算ロジックの地図

計算ロジック・資産クラス・配分を変えるときに、統括役（メインの Claude Code）が最初に読む。
サブエージェント（app-implementer／app-verifier／app-reviewer）には、ここから該当するツールの節と「共通の定義」だけを渡す。

- 設計書は `../../Docs/設計書_v7_25_main.md`（以下「設計書」。版が上がったらこの行を直す）
- 節番号は設計書の見出し。アプリの `CLAUDE.md` の「アーキテクチャの要点」にも運用上の注意がある

## 共通の定義（3ツールが共有する。ここを変えると全部に効く）

| もの | 場所 | 使うところ |
|---|---|---|
| 13資産クラス（My Index 定義） | `src/lib/rb/types.ts` の `ASSET_CLASSES`・`AssetClassKey` | /rb・/portfolio・/risk の採用ボタン |
| 資産クラス（/pf・旧リスク診断用） | `src/logic/portfolioAllocation.ts` の `ASSET_CLASSES`。キー・ラベル・順番は rb/types から作り、色だけここに持つ（v7.25 で13クラスに統一） | /pf（PF診断）・旧リスク診断（`components/assessment/`）。/pf の入力欄は `PfDiagnosisSimplePage.tsx` の `CATEGORIES`（13クラスを含むことをテストで確認） |
| モデル配分（Lv1〜7） | `src/lib/rb/types.ts` の `MODEL_ALLOCATIONS`・`MODEL_META` | /rb・/portfolio・/risk の「このPFを採用する」 |
| 最適PF（DB） | `optimal_portfolios`（`scripts/optimize_portfolios.py --apply` が書く。新興国REITは `EXCLUDED_FROM_MODEL` でモデル配分から除外、v7.25） | `MODEL_ALLOCATIONS` と手で同期 |
| リスクレベルの判定 | `src/logic/pfSimple.ts` の `classifyRiskLevel7`（しきい値は `optimize_portfolios.py` の `EFF_UPPER` と対） | /portfolio・/pf |
| 期待リターン・リスク・相関 | DB `asset_class_params`（`src/lib/assetClassParamsDb.ts`）。取得失敗時は `src/logic/portfolioDiagnosis.ts` の `FALLBACK_*` | /portfolio・/pf・`optimize_portfolios.py` |
| 目標配分（採用PF） | `user_rb_settings`（`src/lib/rb/db.ts` の `saveTargetAllocation`／`fetchTargetAllocation`） | /risk が保存、/rb が読む |

設計書：v7.22「新しいモデル配分」「リスクレベル境界を 20% → 16.5% に変更」「単一資産の上限を新設」、v7.24（モデル配分のレベル食い違い）、§13-64（採用PF＝全ツールのアンカー）

### 対で直すもの
- `optimize_portfolios.py` の結果を DB に反映したら → `MODEL_ALLOCATIONS`・`MODEL_META` も同期し、`python3 scripts/check_model_levels.py` で照合（exit 1 なら不一致）
- `EFF_UPPER` を変えたら → `classifyRiskLevel7` も（`src/logic/pfSimple.test.ts`）
- 資産クラスを足す・変えたら → `rb/types.ts`（`portfolioAllocation.ts` は自動で追随、色だけ足す）、/pf の `CATEGORIES`、/ma の `MaAssetClass`（下）、DB のカラム、教材（実践4 のワークシート・スライド）
- モデル配分が変わったら → 実践4 系の教材のサンプル（`wealth-program/`）も点検（FI_project の CLAUDE.md「教訓」）
- 暗号資産の見分け方のリスト（`src/lib/rb/crypto.ts`）を変えたら → FI_project `personal-monitor/monitor/crypto.py` 側のリストも（同じ中身）

## /rb リバランス

| | |
|---|---|
| 計算 | `src/lib/rb/logic.ts`（乖離 `calculateDeviation`、買い増し／売却の調整、期間、緊急資金、`simulateMonthly`） |
| 積立のみ | `estimateMonthsToRebalance(holdings, target, M)`（FI_project #76、2026-11-12）：売らずに目標配分に着く最小の月数 n。目標より多い現金以外の資産クラス i が 今の額_i ≤ w_i×(T＋M×n) を満たす最小の n（1以上、`ceil((今の額_i/w_i − T)/M)`、誤差 1e-9）。超過クラスが無くても目標どおりでなければ1、目標どおり（全クラスの差が1円未満）なら0、M≤0 なら null。現金は取り崩して不足へ回せるので月数を縛らない。現金以外で目標0%なのに保有があれば積立だけでは戻らない（`{ unreachable: 資産クラス名 }`、画面は `calculateAddAdjustment` で今月の積立先だけ出す）。毎月の配分は `calculatePeriod(holdings, target, n, M)` を最小の n で使う（売却は0） |
| 期間指定 | `calculatePeriod(holdings, target, N, M)`（FI_project #74、2026-11-12）：完了期間 N と毎月の積立 M の両方を使う。目標額は N か月後の総資産 E＝T＋M×N に目標配分を掛けた額。売却＝max(0, 今−目標)、買い＝max(0, 目標−今)、現金は売却ではなく取り崩し（または現金のまま置く）、毎月の操作＝総額÷N。いつもの積立で不足を先に埋め、足りない分だけを売る（売却を最小化）。`simulateMonthly` は同じ計画を丸めずに引き直す（`MonthlyProjection.tsx`）。`calculatePeriodByMonths` は M＝0 の呼び出し |
| 乖離の段階と戻す目安 | 段階は `getSeverity`（2・5・10%、変えない）。戻す目安は `REBALANCE_THRESHOLDS`（5%標準／10%）・`isOverThreshold`（\|乖離\| が目安以上）・`countOverThreshold`。選んだ目安はブラウザ（localStorage `rb.rebalanceThreshold`）だけに保存、DB には持たない |
| 投信の取り込み | `src/lib/rb/mfParser.ts`（マネーフォワードの「資産」ページの貼り付けテキスト。区分名は `allocator.ts` が読む表記に正規化。資産クラスの合計がマイナスなら `clampNegativeHoldings` で0に）、`src/lib/rb/allocator.ts`（`fund_master` で資産クラスに振り分け。cash も `fund_master` から入り、緊急資金の差し引きの対象になる）。暗号資産（預金の区分の行を `src/lib/rb/crypto.ts` の `isCryptoHolding` で判定）は cash に入れず配分の計算の対象外とし（`excluded`、合計は `sumExcludedCrypto`。外した行の名前も表示（`excludedCryptoNames`））、区分の合計の照合には含める |
| 型・定数 | `src/lib/rb/types.ts`（共通の定義を兼ねる） |
| DB | `src/lib/rb/db.ts` |
| テスト | `src/lib/rb/logic.test.ts`、`src/lib/rb/allocator.test.ts`、`src/lib/rb/mfParser.test.ts`（見本は `__fixtures__/mf_assets_sample.txt` と暗号資産入りの `mf_assets_crypto_sample.txt`、架空のデータ）、`src/lib/rb/crypto.test.ts` |
| 設計書 | §13-64（採用PF→/rb の目標配分）、§2 の表（⑥ リバランス）、v7.19 |
| 注意 | 口座（iDeCo/NISA/特定）の概念を持たない。売却が出るときだけ `RebalancePage.tsx` の `SellAccountNote` で注記（アプリ CLAUDE.md「/rb の口座注記」） |
